# Координация работы

## Роли

- Текущий основной чат — единственный координатор: план, объединение изменений, тестирование и выпуск.
- Пользователь самостоятельно запускает Codex Spark только по подготовленной карточке задачи.
- Агенты выполняют независимые ограниченные аудиты и тесты; они не утверждают бухгалтерскую логику.

## Правило Spark

Каждая задача Spark должна содержать:

1. путь, версию и SHA-256 текущего контракта из `contracts/CURRENT.md`;
2. идентификатор и одну цель;
3. точные входные пути;
4. разрешённые для изменения файлы;
5. запрещённые действия;
6. затрагиваемые пункты контракта и проверяемые критерии PASS;
7. формат отчёта и перечень изменённых файлов.

Задача без блока `Контракт` имеет статус `BLOCKED` и не запускается.

Результат Spark не объединяется автоматически. Координатор проверяет diff, запускает тесты и только затем фиксирует commit.

## Новая ошибка пользователя

До изменения кода координатор добавляет ошибку в `contracts/ERROR_REGISTER.md`. Если замечание меняет или уточняет функциональное требование, выпускается новая версия DOCX и обновляется `contracts/CURRENT.md`. Устная договорённость не отменяет зафиксированный контракт.

## Если пользователь уходит

После сообщения пользователя «ухожу» координатор продолжает автономно:

- выполняет текущий утверждённый план;
- использует агентов для независимых задач;
- не расширяет бизнес-правила за пределы контракта;
- не публикует и не загружает проводки в 1С;
- фиксирует результаты, тесты и оставшиеся вопросы в `STATUS.md`.

## Запрет параллельных конфликтов

Два исполнителя не редактируют один файл одновременно. Интерфейс, R005, R001, тесты и упаковка выдаются как отдельные области ответственности.

## Текущее решение PERIOD-001 / FY-001

- Канонический контракт: v0.5 из `contracts/CURRENT.md`.
- Область одного расчёта: одна организация + один полный календарный месяц `YYYY-MM`.
- Год, квартал и произвольный многомесячный диапазон не выдаются как задачи реализации R17.
- Годовые файлы и ZIP могут использоваться как контейнеры источника только для независимо выбранного и доказанного месяца.
- Для года пользователь последовательно запускает `YYYY-01` … `YYYY-12`; автоматический fan-out не планируется.
- Каждая месячная задача независимо проверяет organization/period, R005 evidence, `SourceRowID`/provenance, handoff, R001 result и approval scope. Межмесячное смешение, неттирование и повторное evidence запрещены.
- `FY-001` больше не требует технической реализации годового Service fan-out. Это замена продуктового требования, а не заявление об исправлении annual execution.
- PR #19 `FY-001: register blocked annual structural-control fan-out` не объединяется. Его диагностика остаётся историческим свидетельством.

## Текущее распределение APPROVAL-001

- `S04 / Codex Spark`: ядро реестра, лист `01_Правила`, обратная загрузка, проверки и versioned approved JSON; критерии A17–A22.
- `S05 / Codex Spark`: отдельное пользовательское окно, пять действий и безопасное массовое утверждение; критерии A23–A24; старт только после объединения S04.
- `S06 / Codex Spark`: безопасный preflight порта и быстрый повторный запуск; критерий A16; может выполняться параллельно S04 без общих файлов.
- `C01 / координатор`: контракт v0.4, регистрация ошибки, проверка diff, объединение S04/S05, полный регрессионный прогон и финансовый барьер физического доказательства.
